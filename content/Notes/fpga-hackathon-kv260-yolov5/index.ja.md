以前，[Agile X FPGA hackathon](https://www.agile-x.t.u-tokyo.ac.jp/project/FPGAAIhackathon/)に参加しました．これは
AMD の [Kria KV260](https://www.amd.com/en/products/system-on-modules/kria/k26/kv260-vision-starter-kit.html) を使った FPGA AI デザインハッカソンで、YOLOv5n を FPGA 上で動かし、速度と精度の両立を目指すというものでした．
この記事では，モデルの再学習，DPU 構成の比較，前後処理の高速化について振り返ります．

本競技のスコアは次式で定義されていました。

$$
\mathrm{score} = \mathrm{mAP} \times \mathrm{FPS}
$$

{{< figure src="slide-6.ja.png" alt="ハッカソンにおける我々の戦略" caption="ハッカソンの全体像と我々の戦略" >}}

## Hackathonのベースラインに関して

今回の大会のベースラインは YOLOv3系の実装でした。
事前評価では、シングルスレッドの YOLOv3 実装は **3.8 FPS**, **mAP 47.4%**, score **180** 程度でした。一方で、初期段階で実装した YOLOv3-tiny のマルチスレッド版は、本番動画に対して **52.4 FPS**, **mAP 24.3%**, score **1274** まで伸びました。

mAP が下がっても，FPS の向上によってスコアは大きく伸びました．そこで，モデルの精度と並行して，前後処理や表示を含むパイプライン全体の高速化にも取り組みました．
方針は次の 3 つです．

1. YOLOv5n を再学習して精度を確保する。
2. DPU の構成を比較して、KV260 上で最も throughput が出る設定を探す。
3. ソフトウェア実装をパイプライン化して、I/O と DPU 実行を重ねる。

## モデル選定と学習方針

モデルには，軽量で再学習しやすく，DPU への実装にも見通しが立った YOLOv5n を選びました．

YOLOv5n は CNN ベースで比較的扱いやすく、パラメータ数も少ないモデルです。資料では YOLOv3-tiny の約 4 分の 1 規模とされていて、まず動かして高速化する対象として適していました。さらに Ultralytics の実装が使えるため、ハッカソンの短い期間でも再学習と検証を実施しやすい構成でした。

{{< figure src="slide-11.ja.png" alt="再学習した YOLOv5n とその比較" caption="再学習した YOLOv5n と比較結果。データセットの改善と量子化・枝刈りの影響をまとめて確認しました。" >}}

モデル作成の流れは、おおむね次の通りでした。
1. Ultralytics ベースで YOLOv5n を再学習する。
2. DPU で扱いやすい演算になるようにモデル側を調整する。
3. COCO2017 だけでは足りない分を Open Images v7 で補う。
4. 人クラスの不足アノテーションは YOLOv11 系で擬似ラベルを生成して補完する。
5. 全パラメータの約 30% を枝刈りする。
6. int8 量子化を行い、Vitis AI で `.xmodel` にコンパイルする。

再学習後，枝刈りと量子化を行った際の mAP は次のようになりました．

- 再学習後: mAP 約 45%
- 枝刈り後: mAP 約 40%
- 量子化後: mAP 約 34%

枝刈りと量子化で mAP は落ちましたが，競技のスコアは \(\mathrm{mAP} \times \mathrm{FPS}\) なので，速度向上も含めて判断しました．

## DPU 構成の比較

KV260 上では `B1024 x 2` と `B4096 x 1` を比較し，最終的に **B4096 を 1 基** 使う構成を採用しました．

{{< figure src="slide-12.ja.png" alt="DPU の最適化を比較したスライド" caption="DPU の最適化。B1024 を 2 枚使う場合と B4096 を 1 枚使う場合を比較し、後者を採用しました。" >}}

加えて、B4096 側では **ALU Parallelism を 8** に設定しました。URAM/DRAM や DSP の設定も含めて FPGA リソースをできるだけ使い切る方向で調整しました。

同じ YOLOv5n とソフトウェア実装で比較すると，**B4096 x 1 は B1024 x 2 より全体で約 11% 高速** でした．この構成では，DPU を 2 基使うより，1 基を大きくした方が速い結果になりました．

## ソフトウェア実装の最適化

ソフトウェア側では，推論の流れを次の 3 段階に分けました．

1. `ReadFrame`: 動画からフレームを読み込む。
2. `RunYOLO`: 前処理、DPU 推論、後処理をまとめて行う。
3. `DisplayFrame`: 結果を重畳して表示または出力する。

この 3 段階を独立スレッドにし、間にキューを置いて非同期にデータを受け渡す構成にしました。特に `RunYOLO` は、前処理・推論・後処理をあえて同じスレッド内で処理しています。細かく分割すると、キューに積んだポインタの整合性や画像データの寿命が問題になり、かえって不安定化するためです。

各段の処理時間とキュー占有率を可視化するツールも作りました．これを見ると，DPU より ReadFrame や DisplayFrame がボトルネックになる場面がありました．

{{< figure src="slide-18.ja.png" alt="ソフトウェア全体の最適化を示すスライド" caption="ソフトウェア全体の最適化。ReadFrame、Pre-process、DPU、Post-process、DisplayFrame をまとめて見直しました。" >}}

{{< figure src="slide-14.ja.png" alt="可視化ツールによる性能分析と改善のスライド" caption="可視化ツールによる性能分析と改善。推論だけでなく、ReadFrame と DisplayFrame もボトルネックになりました。" >}}

ここから入れた具体的な改善は次の通りです。

- `ReadFrame`: 動画読み込みを OpenGL 系から `ffmpeg` ベースに寄せて高速化する。
- `DisplayFrame`: 表示処理自体を速くするのではなく、呼び出し回数を間引いて負荷を落とす。
- `PreProcess`: 正規化処理を LUT 化して、CPU 側の前処理を軽くする。
- C++ 実装: メモリ管理やデータ受け渡しの無駄を削り、アイドル時間を減らす。

{{< figure src="slide-17.ja.png" alt="最適化の結果を示すスライド" caption="最適化の結果。ReadFrame は 3 倍、DisplayFrame は 10 倍、DPU 側の推論処理は 3 倍程度高速化しました。" >}}

資料では、ReadFrame のライブラリ切り替えで **約 3 倍**、DisplayFrame の呼び出し間引きで **約 10 倍** の改善がありました。
当初は推論処理での計算処理よりCPUでの前処理と後処理の方が重かったために，
これらの改善は非常に効きました。

## スレッド数とボトルネック

`RunYOLO` は前後処理を CPU で，推論を DPU で行います．DPU の実行中に別のフレームの前後処理を進めるため，RunYOLO のスレッド数を増やして測定しました．

FPS はスレッド数とともに上がりましたが，**4 スレッド前後でほぼ収束** しました．さらに増やした測定でも，ReadFrame 側からの供給が頭打ちになり，余ったスレッドは待機していました．

## 最終結果

最終結果は次の通りでした．

- 本番計測: **177.8 FPS**
- 本番 20 枚評価: **mAP 24.55%**
- 1000 枚での再評価: **mAP 34.37%**
- 大会順位: **2 位**

## 振り返り

FPGA のハッカソンは初参加でした．DPU の高速化だけでなく，動画の読み込みや表示処理にもかなり時間を使いました．各段の処理時間とキュー占有率を測ったことで，どこが詰まっているかを確認しながら改善を進められました．
